**Four problems that the stricter checks exposed.** Making the tests stricter found problems that had been invisible, which is the point of doing it:

- *Checkers that crashed still said PASSED.* The first version of the new S7 trial raised an exception inside the checker, and the verdict file still showed the earlier, passing checks. All six live checkers now turn any exception into a failed check with the traceback.
- *The nine skipped smoke tests had been broken for weeks.* Once they were no longer skipped they failed at import (a missing stub class). They are fixed and run in a ROS-free child interpreter on every build.
- *The bus sometimes "failed" to leave.* In 5 of 20 rush-hour episodes of our first final evidence run the bus docked and boarded correctly, but its trip to the exit ended as `SAFE_STOP POSE_STALE`. The simulator removes a bus that stands within 0.30 m of exit E, while the bus only reported DEPARTED at 0.05 m; with 1 cm of position noise the simulator sometimes won this race. No safety rule was broken, but the S8 checker did not count the departure, so the episodes passed. The trip now ends at 0.25 m, 20 seeded tests reproduce the old fault, and both the S8 completion flag and the T15 verdict require the departure. All evidence was then produced again.
- *A correct restart counted as a fault.* In the next run, 1 of the 25 fault trials failed: vehicle data frozen while reversing (seed 120). The stop was in time (0.98 s, limit 1.25 s), but the checker saw one nonzero command "during the fault". The freeze lasts 2.0 s of simulator time, which ended about 20 ms before 2.0 s of wall-clock time; the data came back, the supervisor released the hold, and the robot rightly moved again while the checker's wall-clock window was still open. For a freeze the window now ends at the first message on the frozen topic after the silence, so motion while the data is really missing still fails the trial. Five unit tests pin the rule, including this exact timing, and the full evidence run was started again on the fixed commit.

## 3. Hub Control Center (final-term user interface)

**What it is.** One web page from which a person chooses any task or sub-task, runs it, watches the hub live and reads the verdict (`docker/hub.sh ui`, then the browser on the same computer). It is a ROS 2 node (`control_center`, package `smart_hub`), not a separate program: it subscribes to the hub's own topics for the live picture and starts tasks exactly as a terminal would (`ros2 launch` / `ros2 run`), so a run from the page writes the same evidence files and is judged by the same checker as a run from the command line.

!img ../figures/ui_live_s8.png | Figure U1 — Hub Control Center during an S8 rush hour started from the page. Left: the request box and the task list by owner. Centre: live map (bus docked at B, robot detouring because obstacle O blocks Cs-J, people in Q). Right: safety, crossing, queue, both forecasts, parking and the mission log. | 16

**Three ways to choose.** (1) The task list: 15 entries grouped by subsystem and owner (S1 to S9, the real-video evaluation, model training, T04, T18, the fault repetition, and the unit tests of one subsystem), each with its own options such as seed, detector, number of trials or dispatch mode. (2) A filter box (task id, topic or a member's name). (3) A request in plain words, for example "robot escort with 3 trials, then S9" or "rush hour reactive seed 3". The request is turned into a plan by a small keyword parser that runs offline inside the node (no network, no language model); the page shows the plan and how sure the match is, and nothing starts until the person confirms. Several tasks are queued and run one after another.

**What makes it part of the system.** The live map is drawn from `/hub/vehicles`, `/crossing/state`, `/parking/state`, `/traffic/edges`, `/hub/queue`, both forecast topics, the planned routes and `/hub/events`; the status tiles show the safety latch and its reason, the owner of crossing C and the two forecasts side by side. When a run ends, the page reads the checker's JSON and lists every check with its measured value (Figure U2), and the History tab keeps earlier runs with their logs. The page shows the commit it runs on.

!img ../figures/ui_result.png | Figure U2 — The verdict panel after a run: every check of the scenario with the measured detail, taken from the same `*_check.json` the command-line run writes. | 12

**Safety and security decisions.** The node has no control authority: it publishes nothing, calls no service and is not part of the reset handshake, so the page cannot move a vehicle or clear a stop; an e-stop behaves the same with or without it. Because the page can start processes, the server is published on the local machine only (127.0.0.1), every option is checked against the task catalogue before a command is built (no shell, no free text in a command), requests must be JSON from the page's own origin, the body size is limited, and the page is served with a strict content-security policy. A run is stopped the way Ctrl+C would stop it (interrupt, then terminate, then kill).

**Verification.** 27 unit tests cover the catalogue, option validation, the request parser, the run queue and the verdict reader. S4, S9 and one S8 episode were started from the page and gave the same results as the command line (11/11, 13/13, 7/7 episode checks).

**Limits.** One run at a time; the request parser knows the hub's vocabulary only and asks instead of guessing when it is unsure; the page is a local tool and has no user accounts.

## 5. ROS graph and interface rationale

All custom types are in `smart_hub_interfaces` (15 messages, 6 services, 3 actions; 14 messages are copied field for field from §6–7 and `SafetyDecision` is our addition, section 12). The full topic/service inventory with rates, QoS and owners is in `docs/INTEGRATION_CONTRACT.md`.

| Interface | Kind | Why this kind |
|---|---|---|
| `/hub/queue`, `/hub/demand`, `/hub/demand_unserved`, `/hub/vehicles`, `/robot/odom` | topics | continuous state streams with several consumers |
| `/hub/safety_decision` | topic (reliable, depth 100) | one numbered record per supervisor tick, so a logger can prove that no record was lost |
| `/robot/cmd_vel_candidate` → `/robot/cmd_vel` | topics (R1) | only the newest command matters; the supervisor is the single gate |
| `/hub/estop`, `/hub/safety` | topics (reliable, transient-local) | a node that starts late must still learn that a stop is active |
| `/safety/clear_stop`, `/scenario/reset` | services | short request/response with an explicit accept/reject reason |
| `/bus/dock`, `/robot/escort` | actions | long missions with feedback, cancellation and a result |
| `/robot/route`, `/bus/route` | topics (`nav_msgs/Path`) | team decision: planned routes for the dashboard and RViz |

Every state message is stamped with its *observation* time, and consumers judge freshness by both stamp and receipt time; unstamped or future-stamped data is never fresh (§5).

## 6. M1-A — passenger detection and queue counting (S1)

**Pipeline.** `/camera/image_raw` → person boxes → foot point (bottom centre) → planar homography from 4 calibrated floor points (DLT) → nearest-neighbour tracking in metres → count of confirmed tracks inside Q, crossing flag for C → `/hub/queue` at 5 Hz. Two detectors: a documented dark-region baseline (`blob`) for the synthetic camera and OpenCV's pretrained HOG people detector (`hog`) for real video (§8.2 step 1).

**Rules (§8.2).** 0.4 s appearance and disappearance debounce; identity kept through 0.5 s occlusion; crossing held occupied until C is clear for 2 s; feed silence or a frozen source stamp for 1 s makes the state invalid (count 0, confidence 0, `valid=false`, crossing reported occupied so nobody is granted entry).

**Results (simulation, synthetic camera from M5).**

| Test | Criterion (§8.3) | blob baseline | HOG |
|---|---|---|---|
| T01 stable counts | 0, 3, 5, 4 after debounce | 0, 3, 5, 4; MAE 0.000 over 130 samples | MAE 0.984 (≤ 1 target met narrowly) |
| T02 no double count | 0.3 s occlusion creates no new id | 6 tracks for 6 people | 4 tracks for 6 people (recall 0.67) |
| T02 freeze | invalid within 1.2 s | 1.067 s | 1.043 s |
| crossing hold | occupied while in C + 2 s | on after 0.42 s, clear 2.31 s after leaving | on after 0.60 s, clear 2.50 s after leaving |

**A failure found and corrected.** The count-versus-truth plot showed that, right after a camera freeze, the count decayed to a *valid* zero for about 0.6 s before the state became invalid, because the disappearance debounce kept running without frames. The count is now judged at the last processed frame; a regression test (`test_silent_feed_never_reports_a_valid_zero`) prevents it from returning. After the fix: 0 valid-zero samples after the freeze.

**Real lab video (§8.3).** A fixed phone filmed the S1 script on a hall floor with the queue and the crossing marked in tape (`IMG_0572.MOV`, 70.4 s, 1920×1080, 30 fps; not measured, so the eight tape corners define Q and C directly and metric distances are approximate). Husan labelled **141 frames** by hand (one every 0.5 s): people with their feet in Q, someone in C, and whether a person in Q was partly hidden by another (`evidence/m1a/real_video/labels_husan.csv`). Two properties of the video shaped the pipeline. First, the phone drifted up to 67 px during the take; `perception/stabilizer.py` aligns every frame to the first one with ORB features on the lower floor and a RANSAC homography (all 2,112 frames aligned; a frame whose alignment fails five times in a row is now marked untrusted instead of silently reusing an old alignment, 0 such frames here). Second, the heads are out of the picture and the camera looks steeply down, which the pretrained OpenCV HOG people detector (whole upright pedestrians) does not handle; we therefore added a second pretrained detector, YOLOv4-tiny (Darknet, COCO class *person*, OpenCV DNN, input 608×352, score threshold 0.5, NMS 0.4; weights downloaded separately, SHA-256 in README_M1A). Tracking, debouncing, the foot point and the zones are unchanged from the simulated pipeline. The configuration (YOLO, stabilised, 8 calibration points) was fixed before scoring.

| count RMSE | 0.438 | 3.223 | — |

The remaining YOLO errors are of two kinds (Figure 3a): one-step lags while people walk into or out of Q, where the 0.4 s confirmation and hold windows and the feet crossing the tape line make the count change a frame or two early or late; and the deliberate hiding test at 37.5–39.5 s, where one person stood directly behind another for 2 s and was not visible at all, so the count stayed at 4 for longer than the 0.5 s occlusion memory — partial occlusion is the main failure mode (MAE 0.83 versus 0.12). HOG detected almost nobody in this view (MAE 2.66) and is reported as the failing baseline. Precision/recall were not computed because no per-person boxes were labelled. The stabilisation ablation is honest in the other direction: without it the MAE was slightly lower (0.114); the five differing frames are all at 63.5–66 s, while people step back over the far edge of Q, where the drift estimate fitted on the lower floor is least exact. Stabilisation stays the documented configuration because it was chosen from the measured drift before scoring, not from these labels.

**Crossing flag, reported properly (final term).** The midterm gave one number, "crossing flag correct", and the review pointed out that it hides the error that matters. The flag has two different mistakes: a *false clear* (a person is in C and the detector says clear, so a vehicle could be let in) and a *false busy* (C is empty and the detector says occupied, so a vehicle waits for nothing). `perception/crossing_metrics.py` now reports both, with the class balance and the timing. Only 13 of the 141 labelled frames have a person in C, so a detector that always answers "clear" scores 90.8 %. That is exactly what HOG does: it never saw the person in C (13 false clears in one episode of 6 to 7 s, recall 0), and its 90.8 % equals the always-clear baseline. YOLOv4-tiny made no false clear; its 4 errors are false busy: one label just before the person stepped in, and three labels (1 to 2 s) after the person left, which is the deliberate 2 s hold. The person entering C was reported on the same label (delay 0.0 s at 0.5 s label spacing) and the flag cleared 1.5 s after the exit. An invalid frame is counted as occupied, never as clear; all 141 frames were valid. This is one recording with a single crossing entry, so it shows that the report works and that the main detector is on the safe side here; it is not a false-clear rate.

## 7. M1-B — AI demand prediction (S2)

Source: `src/smart_hub/results/S2_report.md` and `metrics.json` (synthetic seeded episodes). 50 six-minute episodes over 7 demand profiles, split by whole episode 30/10/10 before windowing; features `q_t`, 10 s and 30 s means, 10 s trend, 30 s arrivals and departures; standardized ridge regression (alpha chosen on validation only); persistence baseline.

**Two targets, two topics (the main review point).** At the midterm the node published one forecast, trained on *unserved demand* (how many people would be waiting in 30 s if no bus came), under the name the assignment reserves for the *future queue*. That target is easier to predict and more useful for dispatch, but it is not what §9 asks for, and calling it by the same name was wrong. Both are now published and evaluated separately:

| T03, 2,500 held-out forecasts | Topic | Ridge MAE | Persistence MAE | Difference (95 % CI, episode bootstrap) |
|---|---|---|---|---|
| Queue at t + 30 s (the assignment's target) | `/hub/demand` | 1.625 | 1.668 | −0.044 (−0.157 … +0.070) |
| Unserved demand at t + 30 s (our extra) | `/hub/demand_unserved` | 1.215 | 1.506 | −0.292 (−0.543 … −0.044) |

The honest reading: on the assignment's own target the model is not worse than persistence (the T03 criterion, MAE ≤ baseline, is met), but the interval includes zero, so we do not claim that it is better. The future queue depends on when the next bus boards, which the features cannot see. On unserved demand the gain is real (better in 7 of 10 test episodes). Inference takes 0.013 ms at p95 (target < 100 ms). The same split, features and export check are used for both models; the model files are `models/queue_ridge_h30.json` and `models/demand_ridge_h30.json`.

**Which one dispatches the bus.** In a paired closed-loop study over 50 seeds (offline policy simulation), dispatching from the unserved-demand forecast lowered the mean passenger wait by 10.0 s against reactive dispatch (95 % CI −14.9 … −6.0), while dispatching from the future-queue forecast changed it by +1.4 s, which is no gain. The coordinator therefore reads `/hub/demand_unserved` (parameter `dispatch_demand_topic`, named in every dispatch event), and `/hub/demand` is published for whoever needs the assignment's quantity. Live in the integrated stack both topics ran at 1.0 Hz on M1-A's `/hub/queue` and became valid after the 60 s warm-up.

## 8. M2-A — bus manager and docking (S3)

`bus_manager` serves the DockBus action and runs the §10.2 state machine IDLE → APPROACH → (WAIT) → DOCK → BOARD → COMPLETE, with SAFE_STOP from every moving state; the logic lives in `bus_core.py` (pure Python, 10 closed-loop tests against the simulator). The bus asks M4's `/route/compute` for its route (1 s timeout, at most 2 retries, then PLANNER_UNAVAILABLE; NO_ROUTE fails at once; a fixed A-N-Cn-B fallback exists only as an off-by-default parameter), asks `/crossing/request` for C 2.5 m before a stop line 0.25 m in front of C, renews every 1 s (3 s lease) and releases once its footprint has left C; when bay B is blocked it waits before C without holding the crossing. Docked = position ≤ 0.20 m, yaw ≤ 0.17 rad and speed < 0.02 m/s for 1 s; the door is requested only then, kept open 8 s from the measured opening, and propulsion needs a measured closed door. ETA = remaining route length / smoothed measured speed + remaining turn time + a declared 1.5 s final-approach allowance; invalid while waiting.

**S3 live** (`docker/hub.sh s3`, `evidence/m2a/s3/`, 12/12 checks, Figure 5). T05: 10/10 dockings on the planner's route A-N-Cn-B, position error at most 0.043 m, yaw error at most 0.005 rad, door open 8.1–8.2 s per stop with no movement while open, crossing granted before entry and released after exit in all 10, no collision, 4 passengers boarded and 1 left waiting each time. ETA error at 5 m remaining: mean 0.19 s, maximum 0.37 s (target ≤ 3 s); ETA invalid 0.1 s per trip (before a credible speed). T06: zero `/bus/cmd_vel` 0.051 s after the cancel was accepted (limit 0.5 s), bus stopped 0.07 s later, status CANCELED, crossing released. A pedestrian in C made the coordinator deny with `PEDESTRIAN_PRESENT`; the bus waited outside C and docked after the person left. A car in bay B gave WAIT with `BAY_BLOCKED` outside C. Freezing the vehicle feed gave a zero candidate after 0.501 s (pose timeout 0.5 s) and SAFE_STOP, then the bus resumed and docked. With seven people in Q the coordinator dispatched the bus by itself (observed-queue fallback) and the mission succeeded. Positions now carry 1 cm of seeded observation noise, so the ten trials are no longer copies of each other. The simulated bus has no inertia, so stopping times are shorter than on hardware.

!img ../../evidence/m2a/s3/s3_paths.png | Figure 5 — S3: bus paths (top) and straight-line distance to bay B over time (bottom). Grey: 10 nominal trials; the flat segments at about 4 m are the bus waiting before crossing C (pedestrian in C, blocked bay). | 15

**Unit tests.** `test_bus_core.py` (31 tests, 20 of them the seeded departure cases) drives the pure state machine in closed loop with the M5 simulator and no ROS: nominal docking within tolerance, crossing acquired before entry / renewed / released after exit, denied crossing → WAIT at the stop line, blocked bay → WAIT without asking for the crossing, cancel → zero command at once, stale pose → hold and resume (and abort after 5 s), ETA error at 5 m, timeout and safety latch, path geometry and parameter validation. `test_sim_core.py` covers boarding (at most four waiting people, only while the door is open and the bus is still at B), and `test_reset_launch.py` checks that bus_manager acknowledges resets and rejects a wrong bus id, an unknown bay and a zero duration.

**Problems found and fixed during development.** (1) The arbiter answers `BAD_TOKEN` for a permission that is already gone; the first version expected a different reason and would have retried RELEASE forever. (2) A permission lost while the bus was inside C would have made it brake in the middle of the crossing; it now never stops inside C on its own. (3) After a stale-pose stop the bus resumed as APPROACH even when it had been boarding; it now resumes the phase it was in. All three were found by review and the closed-loop tests before the live run.

**Departure (final term).** After COMPLETE the bus can be sent to exit E as a separate trip with no docking and no door (§10.2 step 6), reported on its own and used in S8. Section 2 describes the race at the exit that the final evidence run exposed and how it was fixed and tested (20 seeded cases).

**Limitations.** Only bay B is supported. Without an answer from `/route/compute` the bus does not move (T18). A cancel while inside C stops the bus there and keeps renewing the crossing until a new goal drives it out (not tested live). The simulated bus has no inertia.

## 9. M2-B — hub coordinator and S8 integration

`coordinator_core.py` implements crossing arbitration (one owner, 2 s clear debounce, lease HOLD instead of FREE) and the §9.3 dispatch hysteresis; 28 unit tests pass. Verified against the shared interfaces in a scratch workspace: a crossing was granted while `/hub/safety` was fresh and unlatched, and denied with `SAFETY_STOP` after an e-stop. The node runs inside `hub.launch.py` with the rest of the hub; in S3 it granted and released crossing C for the bus and, with seven people in Q, dispatched the bus by itself.

**T04 live** (`docker/hub.sh t04`, `evidence/m2b/t04/`, 6/6 passed). A checker publishes `/hub/demand` at 1 Hz and `/hub/queue` at 5 Hz; the real coordinator and bus_manager do the rest. **What changed in the S8 statistics (final term).** The review made three points about this section, and all three are now in the checker. (1) The midterm wait statistic used boarded passengers only. Each episode has 7 passengers and room for 4, so 3 walk away; dropping them hides exactly the people the system failed. Every passenger is now reported in one of three groups: boarded, walked away, or still waiting when the episode ended. The wait is also given as a Kaplan–Meier median, in which a person still waiting at the end counts as "waited at least this long" instead of being dropped. People who walk away are a different outcome (they gave up), so they are reported on their own with how long they stood in Q before leaving, not mixed into the wait. In this script nobody was still waiting at the end, so the Kaplan–Meier median equals the boarded median, and the 3 people per episode who walked away had stood in Q for 100 to 132 s, longer than any boarded passenger's wait; they leave because the bus is full (capacity 4), in both modes alike. (2) The midterm compared the two modes by their averages; the comparison is now paired by seed with a bootstrap interval. (3) The crossing check now looks at every pair of bodies in C, not only the controlled vehicles, and records each episode of a vehicle and a pedestrian inside C together; a vehicle that keeps moving more than 0.5 s after a person entered counts as a violation. There were none. A fourth change came from the evidence run itself: completion now requires the bus departure (section 2).

**How to read the effect.** The interval excludes zero and every seed points the same way, so predictive dispatch was earlier in this script. The gain is small, about 2 s on a 78 s wait, because the queue jumps from 3 to 7 within about 9 s, so a 30 s forecast has little lead, and the waits are dominated by passengers who arrived during warm-up plus the 38 s bus trip. These are simulation results on one fixed rush-hour shape; they do not establish a transport benefit beyond it.

## 10. M3 — parking and traffic (S4, S5)

Both subsystems follow one pattern: the logic lives in a ROS-free engine (`parking_engine.py`, `traffic_engine.py`, map geometry in `hub_map.py`) that receives the current monotonic time as an argument, and a thin node (`parking_manager`, `traffic_monitor`) adapts it to topics, services, timers and QoS. Both nodes run inside `hub.launch.py`.

**Parking (S4).** The engine keeps the *physical* state (debounced sensor reading) and the *administrative* state (reservation token, vehicle, expiry) apart and derives the effective state on demand: UNKNOWN if the slot was never observed, is older than 1.0 s or a contradicting reading is still being debounced (0.5 s); OCCUPIED if sensed occupied (ownership is kept but never shown as free); RESERVED if a live token exists; FREE otherwise. Only a fresh, debounced FREE slot is allocatable, so UNKNOWN or OCCUPIED slots are never advertised as free (§6.1). Every mutation — validation, request-id cache, slot choice, token creation, expiry — runs under one re-entrant lock, and the two services share one mutually exclusive callback group, so two requests can never interleave (atomicity, §18.2). `request_id` is an idempotency key: the same id with the same payload returns the cached answer, a different payload returns `KEY_REUSE`. The slot is the preferred one if free, otherwise the free slot nearest to access node U by graph distance (P3, P2, P1). One active reservation per vehicle; TTL 5–120 s (default 30 s). Release needs the token and the matching vehicle (`UNKNOWN_TOKEN`, `VEHICLE_MISMATCH`). Expiry and release drop only the administrative reservation and never change the sensed state. A barrier controller opens `/parking/barrier_request` only for a live reservation presented by its own vehicle with a fresh, clear entrance sensor, and closes only after a hold time with the passage continuously clear. Snapshots older than 1.0 s or stamped in the future are dropped, so slots age out to UNKNOWN by themselves.

**Traffic (S5).** Every `/hub/vehicles` snapshot (10 Hz) is gated: the stamp must advance (a repeated stamp is a frozen source), the source age must be within 1.0 s, and each vehicle needs a finite pose, a plausible speed (≤ 1.0 m/s), a map edge id and a position inside that edge's 0.5 m corridor (no silent re-assignment). Obstacles (`kind: obstacle`) are intersected with the corridors. Every 0.5 s each edge gets one label: UNKNOWN when there is no fresh data for more than 1.0 s, during warm-up (3 fresh snapshots) or when a sensor marks a vehicle on that edge invalid; BLOCKED while an obstacle intersects the corridor (kept 2 s after it disappears); CONGESTED when density ≥ 0.70 (n / floor(length / 1.0 m headway)) or the mean of per-vehicle median speeds stays below 40 % of free flow (0.40 m/s) for 3 publications, cleared after 2 publications below; NORMAL otherwise, including an empty edge with a live feed. Invalid edges carry speed and density −1.0, never 0, and the header stamp is the source time of the newest fresh snapshot so consumers can age-check it. A 10 Hz watchdog publishes UNKNOWN as soon as the feed goes stale instead of waiting for the next 2 Hz slot. `/traffic/edges` (EdgeStateArray) has no label field, so labels are also published as JSON on `/traffic/edge_labels` and as `/hub/events` on every transition.

## 11. M4 — routing and robot escort (S6, S7)

**Planner (S6).** `route_planner` serves `/route/compute`; the logic is in `route_core.py` (pure Python). Edge cost follows §13.2: c = L / max(v, 0.05) · (1 + 2ρ) + w, where v is the agent's nominal speed (robot 0.25, bus/car 0.40 m/s) bounded by the measured mean speed from `/traffic/edges`, ρ the measured density (0 on robot-only links) and w a declared crossing wait (5 s) for edges that intersect C while C is occupied, owned by another agent or unknown. Edges are *removed*, not penalised, when they are forbidden to the agent type (§3.1: parking edges car-only, robot links and detour links robot-only), excluded by the caller, reported blocked or invalid by `traffic_monitor`, within obstacle radius + agent radius + 0.05 m of an obstacle in `/hub/vehicles`, or when their observation is stale (traffic > 1.5 s, obstacles > 1 s) — §13.2 "treat stale as blocked". Dijkstra (ties broken deterministically) returns the path, or `NO_ROUTE`. Each answer is published as a `ROUTE_COMPUTED` event with every edge cost used, and all costs at 1 Hz on `/route/edge_costs`.

**Robot (S7).** `robot_manager` serves `/robot/escort`, `/robot/navigate_to` and `/robot/confirm_ready` (std_srvs/Trigger); the logic is in `robot_core.py`. States IDLE → TO_PICKUP → WAIT_READY → ESCORT → ARRIVED with the pauses BLOCKED and WAIT_CROSSING and the terminal states CANCELLED, FAILED and SAFE_STOP. Goals are validated (ids, nodes, duration) and deduplicated by request id; a second goal while busy is rejected. At pickup the robot prompts and waits up to 20 s; readiness is accepted only in WAIT_READY. Routes come only from the planner: 1 s timeout, at most 2 retries, then FAILED PLANNER_UNAVAILABLE; answers to an abandoned attempt are ignored (no stale path); a route that cannot meet the mission deadline fails as DEADLINE_INFEASIBLE. While moving, the remaining route is re-validated against the same edge rules every tick: a removed edge ahead stops the robot at the next node and replans from there; if its own edge is removed it returns to the node it came from (reversal along the edge just used). Congestion-only replans happen at most every 2 s and only for ≥ 15 % lower cost. Crossing C is acquired before the footprint reaches it (stop line 0.2 m before C, or immediately when a reversal starts closer), renewed every 1 s and released once clear; the permission is kept across replans while inside C. Arrival = within 0.20 m for 1 s. Odometry older than 0.5 s gives zero command, after 2 s more SAFE_STOP. Progress = travelled / (travelled + remaining on the current leg), so it may decrease after a detour while the remaining distance follows the new route (§14.3).

## 12. M5 — simulator, safety supervisor and infrastructure (S9)

**Components.** `scenario_runner` (deterministic 20 Hz unicycle simulator, YAML scenarios with seeded events, synthetic camera, fault injection, `/scenario/reset`); `safety_supervisor` (the only publisher of final commands); `actuator_bridge` (independent motor-side watchdog, caps and door interlock); `metrics_logger` (per-run CSV/JSON); `dashboard_marker_publisher` (read-only `/hub/markers`). Each node is a pure-Python core with unit tests plus a thin ROS wrapper.

**Safety policy (§16.2, §18.7).** Every 50 ms on a monotonic clock the supervisor evaluates: stop latch, e-stop heartbeat, freshness of candidate (0.5 s), odometry and vehicle data (1.0 s), clearance, site boundary, door interlock and crossing permission; it then clamps to 0.25 m/s (robot) and 0.40 m/s (bus). Two kinds of stop:

| Kind | Triggers | Ends |
|---|---|---|
| Latch (all agents zero) | e-stop true, footprint outside the site, footprint overlap | only `/safety/clear_stop` when every reset rule passes |
| Hold (affected agent zero) | stale command/odometry/vehicles/e-stop signal, door, clearance, crossing not granted | automatically when the condition is gone |

`/safety/clear_stop` is rejected while the e-stop is asserted or stale, a sensor is stale, a hazard remains, measured speed exceeds 0.02 m/s, or a manager still commands motion; clearing never restarts a mission. A `false` e-stop never clears the latch (§7.1).

**Clearance by stopping distance (final term).** The midterm supervisor looked a fixed 0.5 s ahead, whatever the speed; the review asked why 0.5 s. The clearance is now derived from how far the vehicle needs to stop: d = |v|·τ + v²/(2a), with reaction time τ = 0.25 s (one command period plus transport and actuator delay) and braking a = 0.5 m/s², plus a 0.20 m margin. At the bus limit of 0.40 m/s that is 0.26 m; at the robot limit 0.125 m. Every other body is predicted over the same time: the other controlled agent from the supervisor's own last final command for it (its reported speed has no sign), cars from heading and speed. The parameters are in `config/m5_safety.yaml`. A related gap found by the same review is closed: an agent that leaves C and then reverses back into it needs a new grant (`test_reversing_back_into_the_crossing_needs_a_new_grant`). After the change S3, S7, S9 and the 25 fault trials were run again with 0 violations.

**Three independent stop layers (T17):** supervisor (candidate timeout 0.5 s) → actuator bridge (final-command timeout 0.5 s, own caps) → simulator (drive timeout 0.5 s).

**Reset handshake (team decision, §7.1 "after all nodes acknowledge reset").** `/scenario/reset` installs the new world, broadcasts `SCENARIO_RESET_REQUEST` on `/hub/events`, re-sends it every 0.2 s, and answers only when every participant sent `RESET_ACK`. At the midterm it could take up to 2 s while the clients' timeout was 1 s, so a slow but successful reset could look like a failure to its caller. It now answers within 0.8 s (else `MISSING_ACK: <names>`), the answer carries the measured handshake time, and the repetition test calls it with a 1 s client timeout: 25 of 25 resets answered in time, mean 12 ms, maximum 17 ms. The supervisor keeps its latch across a reset.

**Numbered decision records (final term).** To check "no motion while latched" the midterm logger compared two topics and ignored a 0.1 s window around each latch, because messages on different topics can arrive in either order. A window like that can also hide a real fault. The supervisor now publishes one `SafetyDecision` per tick on `/hub/safety_decision`: a sequence number, the latch, the reason and the final command of every agent, all in one message, so there is nothing to order. The logger checks every record and counts gaps. In the 25 fault trials: 1,813 records, 0 gaps, 0 records with a latch and a nonzero command.

## 14. Evidence and reproducibility

**One commit.** The review found that the midterm evidence came from several revisions. `tools/run_release.sh` now runs everything in order on one commit and stops at the first failure: build, the test suite, S1 with both detectors, S3 (10 dockings), T04, S4, S5, S6, S7 (10 escorts), T18, S9, the 25 fault trials, S8 (20 episodes) and the three lab-video runs; then it writes `evidence/release/versions.txt` (base image digest, OS, ROS and package versions) and `MANIFEST.sha256` (a hash of every evidence file). Every `*_check.json` carries commit 4c89df9, and the run is marked "dirty" if `src/` or `docker/` differ from that commit. Later commits change documents only.

**Re-running.** From a clean checkout with Docker: `docker/hub.sh image`, `build`, `test`, then any of `s1 s3 t04 s4 s5 s6 s7 t18 s8 s9 s9x`, or `docker/hub.sh ui` for the Control Center. Seeds are fixed (S9 seed 9, repetition seeds 101–125, S8 seeds 1–10) and positions carry seeded noise, so runs repeat. Files: `evidence/m1a/` (S1 checks, real-video results and labels), `evidence/m2a/`, `m2b/`, `m3/`, `m4/` (one folder per scenario with check file, CSV traces and plots), `evidence/s8/` (20 episodes, summary, rosbag and dashboard video of seed 1), `evidence/m5/` (S9 check, metrics, rosbag, parameter dumps, 25-trial CSV/JSON), `src/smart_hub/results/` (M1-B). The ZIP also contains the raw lab video, the YOLOv4-tiny model files, `LICENSE` and `THIRD_PARTY_NOTICES.md`.

## 15. Limitations

All scenario results are from the simulator; no physical robot or barrier was used, and "stopped" means the simulated velocity. Vehicles have no inertia, so stop times are shorter than on hardware and the braking value of the stopping-distance rule is declared, not measured. The only real-world data is the M1-A lab video: one camera, one recording, 141 hand-labelled frames, one entry into the crossing, floor zones taken from the tape marks; its results show that the pipeline transfers and that the main detector erred on the safe side there, not a field validation. Synthetic people are simple figures, which favours the blob baseline and handicaps HOG. On the assignment's own forecast target (future queue) the model is not shown to beat persistence. The S8 comparison is paired and its interval excludes zero, but the effect is about two seconds on one fixed rush-hour shape and must not be read as a general transport result. The Control Center is a local tool for one operator.
